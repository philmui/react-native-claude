Worth knowing by heart

The 5 Golden Patterns

These five short patterns build almost every Interview 2 app. Look at one at a time. When you feel ready, switch on Hide the code, try writing the pattern yourself in Snack, and then click or tap the blurred code to compare.

Pattern 1

State from data

Let inference do the typing.

Why it works: State is the memory your screen draws from. When you start useState with real data, TypeScript reads the value and works out the type for you, so menu becomes MenuItem[] with zero extra typing. Only an empty array needs a hint, because TypeScript cannot guess what will go into it. The list lives in App; the form’s name and popular state lives in the form itself (Pattern 4).

// in App
const [menu, setMenu] = useState(menuItems);   // menu: MenuItem[]
// empty array needs a type:  useState<MenuItem[]>([])

Pattern 2

Map data to components

No { right after the arrow means the value is returned.

Why it works: map calls your arrow function once per item and collects whatever it returns into a new array. When there is no { right after =>, the expression is returned automatically; the ( ) around the JSX are just grouping so it can span several lines. A { right after => starts a function body, so you must write return yourself. The key lets React tell the cards apart: use a unique id if the data has one (key={item.id}); key={item.name} is fine only if names are unique.

const cards = menu.map((item) => (
  <ItemCard key={item.name} item={item} />
));
// ...then inside JSX:  <ScrollView>{cards}</ScrollView>

// Same thing with a block body: braces need return
const cards2 = menu.map((item) => {
  return <ItemCard key={item.name} item={item} />;
});

// The card itself: typed props, destructured
const ItemCard = ({ item }: ItemCardProps) => (
  <View style={styles.card}>
    <Text>{item.name}</Text>
    {item.popular && <Text>Popular</Text>}
  </View>
);
// item.popular is a boolean, so && is safe (numbers are the danger)

Pattern 3

Add to an array immutably

Make a new array; never push into the old one.

Why it works: React re-renders when you hand the setter a new array. [...menu, item] copies every old item into a fresh array and puts the new one at the end. Because state here is an array, you use square brackets [ ], not curly braces. The updater form is also valid and is safer when the next value depends on the previous one.

const addMenuItem = (item: MenuItem) => {
  setMenu([...menu, item]);
  // also valid: setMenu((prev) => [...prev, item]);
};
ConceptPracticeCheat sheet
Pattern 4

Callback down, call it up

The parent owns state; the child just asks for changes.

Why it works: Data flows one way: down through props. To change the parent’s state, the parent passes a function down as a prop, and the child calls it. The child calls it from a handler that runs on press (not during render) and builds the exact object the type expects. Writing onPress={onAdd(item)} would call it during render instead, which can cause “Too many re-renders”.

Parent// Parent (App): owns the list
const addMenuItem = (item: MenuItem) => {
  setMenu([...menu, item]);
};
<AddItemForm onAdd={addMenuItem} />
Child// Child: owns the text field and switch
const AddItemForm = ({ onAdd }: AddItemFormProps) => {
  const [name, setName] = useState("");
  const [popular, setPopular] = useState(false);
  const handleAdd = () => {
    if (name.trim() === "") return;
    onAdd({ name, popular });
    setName("");
    setPopular(false);
  };
  return (
    <View>
      <TextInput value={name} onChangeText={setName} placeholder="Item name" />
      <Switch value={popular} onValueChange={setPopular} />
      <Pressable onPress={handleAdd}><Text>Add</Text></Pressable>
    </View>
  );
};

Pattern 5

Controlled inputs

The input shows state; typing updates state.

Why it works: A controlled input reads its value from state and reports every change through a callback. onChangeText hands you the new string, so passing setName directly works, and so does the arrow version. Switch works the same way with a boolean.

<TextInput value={name} onChangeText={setName} placeholder="Item name" />
// equivalent: onChangeText={(text) => setName(text)}

<Switch value={popular} onValueChange={setPopular} />

Common trap: setMenu((menu) => {...menu, item}) looks close but has two problems. Braces right after => start a function body, not an object, and the state is an array, so you need [...menu, item]. Also, call the setter you actually declared (setMenu), not a generic name.

Right before you walk in

Interview day

Interview-day essentials

In one sentenceThey are watching how you think and debug, not whether you finish, so talk aloud, read the errors, and search for knowledge rather than answers.

Open whichever part you need.

The format
  • 25 minutes on one programming problem, in Expo Snack on your laptop.
  • You get a handout with a reference screenshot and a step-by-step breakdown.
  • You can ask clarifying questions at any point. The TA may also ask you to move on to another part.
  • The focus is your process, not the final code. You are not expected to finish the whole problem.
  • Pencil and paper are provided if you want to sketch the layout first.
Allowed resources
  • The open internet, including the Google Search AI overview.
  • One page of handwritten notes in English, front and back, pen and paper only. You turn it in at the end. (You do not need notes to do well.)

Not allowed

  • Any other AI tools, such as chatbots or code assistants.
  • Homework solutions, including solution-like code written by hand on your notes page.
Before and during
  • Arrive 5 minutes early with a charged laptop. Delays come out of your 25 minutes.
  • Think aloud. Saying “I expect this to show three cards” helps the TA see where you are and point things out.
  • Read error messages slowly. They often name the exact problem, like Text strings must be rendered within a <Text> component.
  • Write it in JavaScript first, run it often, and add TypeScript types once it works.
  • If the interviewer says move on, stub the unfinished part with hard-coded values (for example, a fixed array instead of state) and come back to it later.
A 60-second talk-aloud script
  1. “Let me read the whole handout first and sketch the screen.”
  2. “The data is a list of items, so I’ll write a type with name and popular.”
  3. “The list lives in App, because the form needs to add to it and the cards need to show it.”
  4. “I’ll get static cards on screen first, then map over state, then the form and the callback.”
  5. “I’ll run it after each step. I expect three cards now… I see three, good.”
Snack tips
  • Red squiggles usually do not stop the app. TypeScript errors are warnings in Snack, which is why “JavaScript first, types second” works.
  • The web preview is not a phone. Text outside <Text> or a stray 0 may only crash on iOS or Android.
  • On the red error screen, read the message and the line number before changing anything.
  • onChangeText={setName} is fine because it passes a string. onPress={setX} is not the same: it passes an event object, so write onPress={() => setX(true)}.
