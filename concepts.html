Mental model

Components are functions React calls

In one sentenceA component is a function that React calls to get JSX; when state changes, React calls it one more time and the screen shows the new result.

When you write const App = () => { ... }, you are not drawing the screen yourself. You are writing a render function: a recipe that says "given the current data, here is what the screen should look like." React calls that function for you, takes the JSX it returns, and draws real native views on the phone.

The key word is calls. React calls your component function on the first render, and it calls it each time something it tracks changes. Every call runs your whole function body from top to bottom: every const is created fresh, every map runs, and a fresh JSX tree comes back. People summarize this as UI = f(state): the screen is a function of your state.

Why a normal variable does not work

Lecture 3a shows two tempting attempts to remember a count. Both look reasonable, and both break for different reasons. Understanding why they break is the whole reason useState exists.

Attempt 1 · local letconst App = () => {
  let count = 0;
  return (
    <View>
      <Text>{count}</Text>
      <Button title="+1" onPress={() => (count += 1)} />
    </View>
  );
};

Problem: it resets. The tap does change count, but nothing tells React to draw the screen one more time. And even if React did re-render, the very first line of the function body runs let count = 0 from scratch. A local variable lives only for one call of the function.

Attempt 2 · top-level letlet count = 0;

const App = () => {
  return (
    <View>
      <Text>{count}</Text>
      <Button title="+1" onPress={() => (count += 1)} />
    </View>
  );
};

Problem: React never hears about it. This variable survives between renders, but changing it is invisible to React. React only re-renders when you call a state setter. So the number increases in memory while the screen keeps showing 0.

What works · useStateimport { useState } from "react";
import { View, Text, Button } from "react-native";

export default function App() {
  const [count, setCount] = useState(0);   // React remembers this between renders
  return (
    <View style={{ padding: 40 }}>
      <Text>{count}</Text>
      <Button title="+1" onPress={() => setCount(count + 1)} />
    </View>
  );
}

useState solves both problems at once. React stores the value outside your function, so it survives each call, and the setter tells React to re-render, so the screen catches up. (A general tip: always call the setter you actually declared, here setCount, not a generic setState.)

What this mental model buys you in the interview. When something on screen is "stuck," ask two questions: Is this value in state? and Did I call the setter with a new value? Those two questions explain most "nothing happens when I tap" bugs.
Common trap: expecting the variable to change right away. Calling setCount(1) does not change count on the next line. It asks React for a new render, and only that render sees the new value. A console.log(count) right after the setter prints the old number. See the snapshot simulator in the useState topic.
You use Attempt 1 (a local let count = 0) and tap the +1 button three times. What does the screen show?
The arrow function really does run and really does change the local variable. But only a state setter triggers a re-render, and each render starts the function over with let count = 0. Use useState for anything the screen should remember.

Arrow functionsinteractive

Arrow functions are values you can pass around

In one sentenceAn arrow function is a function without a name that you can store or pass like any value; if there is no curly brace right after the =>, the expression after it is returned automatically, and if a curly brace follows the =>, it starts a function body where you must write return.

In JavaScript, functions are values, just like numbers and strings. You can put one in a variable, hand it to another function, or give it to a component as a prop. An anonymous function is simply a function that does not have its own name. Arrow functions, written with =>, are the usual way to write one.

You use them constantly in React Native, mostly without noticing: the function you give to map, the function in onPress, the function in onChangeText, and the updater you can pass to a setter. If arrow functions feel automatic, half of the interview gets easier.

Two body styles: expression vs block

An arrow function has one of two kinds of body. An expression body is a single value after the arrow, and that value is returned automatically (this is called an implicit return). A block body starts with a curly brace {; it can hold several statements, and it returns undefined unless you write return yourself.

const names = menu.map(item => item.name);

Returning an object: wrap it in parentheses

This is the single most common arrow-function surprise. Curly braces have two jobs in JavaScript: they start an object literal { name: "Pie" }, and they start a block of statements. Right after =>, JavaScript always picks block. So if you want to return an object from a concise arrow, you must wrap the object in parentheses: () => ({ name, popular }). The parentheses tell JavaScript "this is an expression," and inside an expression, braces can only mean an object.

Wrong · braces start a block// Intended: copy the menu and add item
setMenu((menu) => {...menu, item});
// "{" after => starts a block body.
// "...menu, item" is not a statement,
// so this is a syntax error.
Right · return a new array// State is an ARRAY, so build an array:
setMenu((prev) => [...prev, item]);

// Or the simple direct form:
setMenu([...menu, item]);

Notice that the fix above has two parts. The braces after => were the syntax problem, but the menu is an array, so the right shape is [...prev, item] with square brackets. Adding parentheses to get ({...menu, item}) would run, but it would turn your array into a plain object with keys 0, 1, and item. The spread topic and the useState topic dissect this example line by line.

Square brackets right after the arrow are not a block, so this is an expression body that returns a brand-new array. This is exactly the shape a menu updater needs.

Passing a function vs calling it

Props like onPress want a function to call later, when the user taps. There are three shapes you will write, and the difference between them is just a pair of parentheses. Writing a function's name, handlePress, passes the function. Writing handlePress() calls it right now, during render, and passes whatever it returns. Wrapping it in an arrow, () => addItem(item), creates a brand-new small function that will call addItem(item) later. That last form is how you pass an argument.

Good · pass or wrap// pass the function itself (no argument needed)
<Pressable onPress={handlePress}>

// wrap in an arrow when you need an argument
<Pressable onPress={() => addItem(item)}>

// onChangeText already gives you the text,
// so both of these are equivalent:
<TextInput onChangeText={setName} />
<TextInput onChangeText={(text) => setName(text)} />

// "Too many re-renders. React limits the
//  number of renders to prevent an
//  infinite loop."

Common trap: onPress={addItem(item)}. It looks like "when pressed, add the item," but the parentheses call addItem the instant React renders the component. Read => out loud as "later": () => addItem(item) means "later, add the item."
You have const removeItem = (name: string) => { ... }. Which onPress removes "Fries" only when tapped?
The arrow wraps the call so it happens later, with the argument you chose. Option 1 calls it during render. Option 2 passes the function, but Pressable would call it with a press event, not the string. Option 4 mentions the function inside a block but never calls it.
Extra detail: arrow functions with TypeScript types

When you write an arrow function on its own, TypeScript needs parameter types. When you pass an arrow straight into map or onChangeText, TypeScript already knows the types from context, so you can leave them off.

// standalone: annotate the parameter
const addMenuItem = (item: MenuItem) => {
  setMenu([...menu, item]);
};

// passed into map: item is inferred as MenuItem
const names = menu.map((item) => item.name);

// the TYPE of a function value (used for props):
type AddItemFormProps = { onAdd: (item: MenuItem) => void };

map & listsinteractive

map turns an array of data into an array of components

In one sentencemenu.map((item) => ( <ItemCard key={item.name} item={item} /> )) runs your arrow function once per item and gives back a new array of JSX, which React renders when you put it inside { }.

map is a method every array has. You give it a function, it calls that function once for each element, and it collects whatever your function returns into a new array of the same length. The original array is not changed. Lecture 4a introduces it with numbers: [1, 2, 4, 8, 16].map(x => x * 2) gives [2, 4, 8, 16, 32].

React adds one twist: if your function returns JSX, you get an array of JSX elements, and React knows how to render an array placed inside curly braces. That is how one data array (the shopping-cart fruit list, a menu, a feed of posts) becomes a list of cards on screen.

The two syntaxes (both correct)

Because map takes an arrow function, the two arrow body styles show up here. Most of the time you will use the no-braces version: there is no { right after =>, so the JSX is returned automatically. The parentheses around it are just grouping, so the JSX can span several lines. Switch to the braces version only when you need a statement before the JSX, such as computing a label. With braces, the return is mandatory.

One-liner · no brace after =>, returned automaticallyconst cards = menu.map((item) => (
  <ItemCard key={item.name} item={item} />
));
Block body · braces need returnconst cards = menu.map((item) => {
  const label = item.popular ? "★ " + item.name : item.name;
  return <Text key={item.name}>{label}</Text>;
});

The forgotten-return bug

This bug is silent, which is what makes it nasty. If you open braces and forget return, your function still runs for every item, creates the JSX, and then throws it away. Each call returns undefined, so map hands back [undefined, undefined, undefined]. React renders undefined as nothing. No red screen, no warning, just an empty list.

Bug · braces, no returnconst cards = menu.map((item) => {
  <ItemCard key={item.name} item={item} />;
});
// cards is [undefined, undefined, undefined]
// the screen shows no cards
Fix · either one// add return
const cards = menu.map((item) => {
  return <ItemCard key={item.name} item={item} />;
});

// or switch the braces to parentheses
const cards = menu.map((item) => (
  <ItemCard key={item.name} item={item} />
));

The key prop: a name tag for each item

When a list re-renders, React compares the new array of elements with the previous one. A key is a stable, unique label that lets React match "this card now" with "that card before," so it can add, remove, or reorder just the right ones. Without keys, React prints the warning Each child in a list should have a unique "key" prop.

  • Where it goes: on the outermost element you return from map, for example <ItemCard key={item.name} ... />. Not inside ItemCard.
  • What to use: a unique id if the data has one (key={item.id}). key={item.name} is fine only if names are unique, which is true for the small menus on this page. Never Math.random(), which changes every render.
  • Index as key: key={index} silences the warning but can mix up items when you insert, remove, or reorder, so do not use it as your default. It only works safely for a list that never changes.
  • Not a real prop: ItemCard cannot read props.key. If the child needs the value, pass it separately.

Where the result goes: a variable or inline

Both patterns render the same thing. Storing the cards in a variable keeps your return short and readable, which helps when you are explaining your code out loud. Inline is also common; just mind the extra brackets.

The index parameter, and filter / find

map also passes the position as a second argument, which is handy for numbering. Two cousins come up often: filter keeps only the items whose function returns true (also a new array), and find returns the first matching item or undefined. You can chain them: filter first, then map.

// index as the second parameter
const numbered = menu.map((item, index) => (
  <Text key={item.name}>{index + 1}. {item.name}</Text>
));

// only popular items, then cards
const popularCards = menu
  .filter((item) => item.popular)
  .map((item) => <ItemCard key={item.name} item={item} />);

// first match, or undefined
const fries = menu.find((item) => item.name === "Fries");
Common trap: braces in filter too. menu.filter((item) => { item.popular }) returns undefined for every item, and undefined counts as false, so the result is an empty array. Same rule as map: with no brace right after => the value is returned automatically; braces start a body that needs return.
Which of these renders no cards at all?
Braces start a block body, and without return every call gives undefined. The other three return the JSX: the first and last with an implicit return, the third with an explicit one.
Where should key go?
Keys belong on the outermost element of each item in the array that map returns, because that array is what React compares between renders.

Objects, destructuring, and the spread operator

In one sentenceTo change an array or object in state, build a new one with spread ([...menu, item] for arrays, { ...item, popular: false } for objects) instead of editing the old one, because React only re-renders when it sees a new reference.

Objects and how to read them

An object groups named values: const fries = { name: "Fries", popular: true };. Each name is a property. You read one with dot access, fries.name, or with bracket access, fries["name"], which is useful when the property name is in a variable. A menu is just an array of these objects.

Destructuring: unpack by name or by position

Destructuring is a shortcut for pulling values out into variables. Curly braces unpack an object by property name. Square brackets unpack an array by position. You already use both every day in React: ({ item }) in a component's parameters is object destructuring of the props, and const [count, setCount] = useState(0) is array destructuring, because useState returns a two-element array.

const fries = { name: "Fries", popular: true };

// object destructuring: by NAME
const { name, popular } = fries;      // name = "Fries", popular = true

// array destructuring: by POSITION
const pair = ["Fries", "Shake"];
const [first, second] = pair;         // first = "Fries", second = "Shake"

// the same two ideas in React
const ItemCard = ({ item }: ItemCardProps) => <Text>{item.name}</Text>;
const [menu, setMenu] = useState(menuItems);

// shorthand when building an object: { name, popular } means
// { name: name, popular: popular }
const newItem = { name, popular };

Spread: copy everything, then add or override

The three dots ... are the spread operator. Inside square brackets they copy the elements of an array into a new array. Inside curly braces they copy the properties of an object into a new object. After the spread you can add more elements, or override a property. When the same property appears twice, the later one wins, so put your override after the spread.

Common trap: the wrong brackets. If menu is an array, { ...menu, item } does not add to the list. It builds a plain object like { 0: fries, 1: shake, item: pie }, and menu.map then crashes because objects do not have map. Arrays use [ ]; objects use { }. The reverse mistake, [...someObject], throws TypeError: ... is not iterable.

Immutable update recipes

Immutable means "never change the original; make a changed copy." These five recipes cover nearly every list update you will write in the interview. Each one produces a new array, so React sees the change.

GoalWrite thisAvoid (mutates)
Add to the endsetMenu([...menu, item])menu.push(item)
Add to the startsetMenu([item, ...menu])menu.unshift(item)
Remove onesetMenu(menu.filter((m) => m.name !== target))menu.splice(i, 1)
Update onesetMenu(menu.map((m) => (m.name === target ? { ...m, name: newName } : m)))menu[i].name = newName
Toggle a booleansetMenu(menu.map((m) => (m.name === target ? { ...m, popular: !m.popular } : m)))m.popular = !m.popular

The toggle recipe combines three ideas: map visits every item, a ternary (condition ? a : b) picks the one to change, and { ...m, popular: !m.popular } copies it with the flag flipped. Every other item is returned as is. (In these recipes, target is the name of the item you want to change.)

One more recipe needs no setter at all. Values you can compute from state, such as a count, should be calculated during render instead of stored in extra state: const popularCount = menu.filter((m) => m.popular).length;. Because the component re-runs on every render, the count is always up to date.

Why mutation does not re-render

Arrays and objects are stored by reference: a variable holds an arrow pointing to a box in memory, not the box itself (Lecture 4b). When you call a setter, React compares the old and new values with Object.is. For arrays that asks "is this the same box?", not "are the contents the same?" If you push into the existing box and pass that same box back, React sees the same reference and skips the re-render. A spread creates a new box, so React notices.

useState: memory that triggers a re-render

In one sentenceconst [menu, setMenu] = useState(menuItems) gives you the current value and a setter; calling the setter with a new value (or with an updater function) asks React to re-render, and the new value appears on that next render.

useState is a Hook: a special React function whose name starts with use and which you call at the top of your component. You give it an initial value, and it returns a pair that you unpack with array destructuring. The first item is the state variable for this render. The second is the setter, the only correct way to change it.

State is a snapshot

Each render gets its own fixed copy of state, like a photo. Inside one render, count never changes, even after you call setCount. The setter queues a change and asks for a new render; the new value shows up in that next render's snapshot. React also batches: it waits until your whole event handler finishes, then re-renders once.

That leads to a famous puzzle. If a handler calls setCount(count + 1) three times, every call reads the same snapshot (say count is 0), so all three say "set it to 1." The updater form, setCount((c) => c + 1), is different: you pass a function, and React feeds each one the result of the previous one in the queue. Try both.

Direct form vs updater form: both are valid

Lecture 5a teaches two ways to call any setter. The direct form passes the new value: setMenu([...menu, item]). The updater form passes a function that receives the previous value and returns the next one: setMenu((prev) => [...prev, item]). Both are correct React.

The updater is a normal arrow function, so all the arrow rules apply. In particular, it must return the next state. That is exactly where the most common broken line goes wrong.

Dissecting a classic broken update

Where state lives

Put state in the component that needs it. If two components need the same data (the form that adds items and the list that shows them), move the state up to their closest common parent and pass it down. That idea, called lifting state up, is the heart of the callbacks topic. Also remember the Rules of Hooks: call useState at the top level of the component, never inside an if, a loop, or a handler.

Common trap: reading state right after setting it. setMenu([...menu, item]); console.log(menu.length); logs the old length. That is expected. If you need the new array right away, store it first: const next = [...menu, item]; setMenu(next); and use next.

Components & props

Custom components and props

In one sentenceA custom component is a capitalized function that receives one props object and returns JSX; writing <ItemCard item={fries} /> makes React call ItemCard({ item: fries }).

Once your screen has repeated pieces (a card per menu item, a post per tweet in the Lecture 4b "Twitter" app), you pull each piece into its own component. A component is just a function whose name starts with a capital letter. It takes one argument, an object called props (short for properties), and it returns JSX.

The attributes you write in JSX become the properties of that props object. <ItemCard item={fries} /> means "call ItemCard with { item: fries }." Inside the component you read props.item, or, more commonly, you destructure it right in the parameter list: ({ item }).

One parent

Styles

Capital names

Callbacks & data flowinteractive

Data flows down, events flow up

In one sentenceKeep the state in the parent, pass both the data and a handler function down as props (<AddItemForm onAdd={addMenuItem} />), and let the child call that handler inside an arrow function (onPress={() => onAdd({ name, popular })}).

React uses one-way data flow (Lecture 4b). A parent can hand data to a child through props, but a child cannot reach up and change its parent's state, and siblings cannot talk to each other directly. So when a form needs to add an item to a list that another component displays, the list's state has to live in their closest common parent. Moving it there is called lifting state up.

How does the child change something it does not own? The parent passes down a function as a prop. A function passed this way is called a callback: the child "calls back" into the parent when something happens. The child does not know or care what the function does; it just calls onAdd with a new item. The parent's function then calls the real setter. This is the same pattern as TextInput's value and onChangeText: data in, an event function out.

TextInput, Switch, Pressable and Button

In one sentenceAn input is "controlled" when state holds its value: you pass the state in with value, and you write the new value back into state from onChangeText (TextInput) or onValueChange (Switch).

Almost every interview handout has a little form: a box to type a name, a switch for a yes/no option such as popular, and a button that adds the item to a list. The good news is that all three use the same idea. State is the single source of truth, the component only displays that state, and every time the user does something, React Native calls a function you gave it so you can update the state.

Here is the loop for a TextInput. You type one letter. React Native calls your onChangeText function with the whole new string (not just the letter). Your function stores it with the setter. The component re-renders, and value={name} now shows the new text.

Common trap.
  • onChange instead of onChangeText. onChange hands you an event object, so your state fills up with an object instead of a string. In the interview, always reach for onChangeText.
  • value={name} with no change handler. The box is controlled but nothing ever updates name, so it looks frozen.

In one sentencePick the tool by the shape of the choice: cond ? <A /> : <B /> for "A or B", cond && <A /> for "A or nothing" (with a real boolean on the left), and an if/else into a variable when the logic gets longer.

JSX is just JavaScript values, so "conditional rendering" means choosing which value to put on the screen. You already know the tools from plain JavaScript; the only new thing is that the values happen to be components.

TypeScriptCore

Types on top of working JavaScript

In one sentenceWrite JavaScript that runs, let TypeScript infer what it can, and then add types in the three places it cannot guess: function parameters and props, callback props, and empty arrays or null starting values.

TypeScript is a superset of JavaScript. Any JavaScript you write is also valid TypeScript syntax (the checker may still complain about it); TypeScript only adds optional labels, called types, that describe what shape a value has. A tool called the type checker reads those labels and underlines code that does not match. In Snack, those are the red squiggles. They are warnings from the checker, not crashes: Snack strips the types before running, so the app often still runs with a squiggle on screen. A red error screen in the preview, on the other hand, is always a real runtime error.

That gives you a calm, three-layer workflow. You never have to get the types right before anything works.

A type alias (type) gives a name to any type. An interface gives a name to an object shape. For the objects you will write in the interview, they are interchangeable, so pick one and be consistent. This kit uses type, because it can also name things an interface cannot, such as a union of strings.

Function types: describing callbacks

A function type looks like an arrow function with types instead of a body. Read (item: MenuItem) => void as "a function that takes one MenuItem and returns nothing useful". void means "returns nothing". A callback with no inputs is () => void. The parameter needs a name as well as a type: in (MenuItem) => void, TypeScript reads MenuItem as the parameter's name with no type, and reports Parameter has a name but no type. Did you mean 'arg0: MenuItem'?

useState and the empty array

When you write useState(menuItems), TypeScript looks at menuItems and infers MenuItem[]. When you write useState([]), there is nothing to look at, so TypeScript infers never[]: "an array that can never hold anything". The first time you try to put an item in it, you get an error like the one below. The fix is to tell useState the type in angle brackets. That angle-bracket slot is called a generic, or type argument.

// to type 'never'.

// Starting from real data? No type needed:
// useState(menuItems) is already MenuItem[]

The same rule applies to "nothing selected yet" values. useState(null) can only ever be null, so write useState<MenuItem | null>(null).

StyleSheet, the box model and Flexbox

In one sentenceIn React Native every View is a flex container whose default direction is column, so justifyContent moves children along that main axis (vertically by default) and alignItems moves them along the cross axis.

StyleSheet and style arrays

Styles in React Native are JavaScript objects with camelCase names: backgroundColor, not background-color. Sizes are plain numbers, measured in density-independent pixels, not strings like "12px". You collect them with StyleSheet.create, which keeps them out of your render code and lets the editor check property names. A style prop can also take an array; when two entries set the same property, the last one wins.

Worksconst styles = StyleSheet.create({
  card: { padding: 12, borderRadius: 12, backgroundColor: "#fff" },
  popularCard: { backgroundColor: "#fdeef6" },
});

<View style={[styles.card, item.popular && styles.popularCard]} />
// popular items: the second entry overrides backgroundColor

The box model

Every component is a box with four layers, from the inside out: the content, the padding (space inside the border), the border, and the margin (space outside, pushing neighbors away). In React Native, a width or height includes the padding and the border, so adding padding never makes the box bigger than the size you set.

Flexbox: two axes

Flexbox is the system that arranges a container's direct children. It always has two axes. The main axis is the direction children are stacked in, set by flexDirection. The cross axis is perpendicular to it. justifyContent works on the main axis; alignItems works on the cross axis. In React Native the default flexDirection is "column", unlike the web, where it is "row". So in a plain View, justifyContent: "center" centers things vertically. Switch to "row" and the axes swap.

Hooks, useEffect, timers and Promises

In one sentenceuseEffect(setup, deps) runs your setup function after React draws the screen, the dependency array decides when it runs next, and the function you return cleans up (for example, clearInterval) before the next run and when the component goes away.

The rules of hooks

A hook is a special React function whose name starts with use: useState, useEffect, and so on. React keeps track of hooks by the order they are called in, so that order must be identical on every render. That gives three rules:

  1. Call hooks at the top level of your component, before any early return, and never inside an if, a loop, or an event handler.
  2. Call hooks only from components (or from your own custom hooks), not from ordinary helper functions.
  3. Hook names start with use. That is how you and React can tell them apart from normal functions.
Bug: hook inside a handlerconst handleAdd = () => {
  const [name, setName] = useState("");
  // "Invalid hook call"
};
Works: top of the componentconst AddItemForm = () => {
  const [name, setName] = useState("");
  const handleAdd = () => { /* use name here */ };
  // ...
};

Anatomy of useEffect

An effect is code that keeps your component in sync with something outside React, such as a timer or a server. You do not call it yourself; React calls it after the screen has been drawn. It has three parts.

The dependency array

You writeThe effect runs…Typical use
useEffect(fn) (no array)after every renderRarely what you want. Setting state in here can loop forever.
useEffect(fn, [])once, after the first renderStart a clock, fetch data when the screen opens.
useEffect(fn, [a, b])after the first render, and whenever a or b changedStart or stop a timer when running changes; refetch when a search term changes.

setTimeout once, setInterval repeatedly

Both take a callback function and a delay in milliseconds (1000 ms = 1 second), and both return an ID you use to cancel them. setTimeout fires one time. setInterval keeps firing until you call clearInterval(id).

The timer example (writing sprint app)

This is the shape of the writing sprint timer from Lecture 5a: a countdown that starts and pauses. The effect depends on running. When running turns true, setup starts an interval. When it turns false (or the screen closes), the cleanup clears the old interval first.

Works · App.tsximport { useState, useEffect } from "react";
import { View, Text, Pressable, StyleSheet } from "react-native";

export default function App() {
  const [seconds, setSeconds] = useState(60);
  const [running, setRunning] = useState(false);

  useEffect(() => {
    if (!running) return;                // paused: start nothing
    const id = setInterval(() => {
      setSeconds((s) => (s > 0 ? s - 1 : 0)); // updater form: uses the latest value
    }, 1000);
    return () => clearInterval(id);      // cleanup: stop this interval
  }, [running]);

  return (
    <View style={styles.container}>
      <Text style={styles.time}>{seconds}s</Text>
      <Pressable style={styles.button} onPress={() => setRunning(!running)}>
        <Text style={styles.buttonText}>{running ? "Pause" : "Start"}</Text>
      </Pressable>
    </View>
  );
}

const styles = StyleSheet.create({
  container: { flex: 1, justifyContent: "center", alignItems: "center", gap: 20 },
  time: { fontSize: 56, fontWeight: "bold" },
  button: { backgroundColor: "#ff7f50", paddingVertical: 12, paddingHorizontal: 28, borderRadius: 12 },
  buttonText: { color: "#fff", fontWeight: "bold", fontSize: 18 },
});

Why the updater form matters here: the stale closure

A closure is a function that remembers the variables around it at the moment it was created. The interval's callback is created once, during the render where the effect ran, so it remembers seconds from that render. With an empty [] dependency array, the effect never runs a second time, so the callback never sees a newer value. It keeps computing 60 - 1 forever, and the clock gets stuck on 59.

Bug: stuck at 59useEffect(() => {
  const id = setInterval(() => {
    setSeconds(seconds - 1); // seconds is always 60 here
  }, 1000);
  return () => clearInterval(id);
}, []);
Works: updater formuseEffect(() => {
  const id = setInterval(() => {
    setSeconds((s) => s - 1); // React passes the latest value
  }, 1000);
  return () => clearInterval(id);
}, []);

Both forms of the setter are valid React. The direct form, setSeconds(59), is the simplest default in event handlers. The updater form, setSeconds((s) => s - 1), asks React to hand you the most recent value, which makes it the safe choice whenever the new value depends on the old one inside a timer.

Promises: values that arrive later

A Promise is an object that stands for a result that is not ready yet, such as data from a server. It starts out pending. Later it either resolves (succeeds, with a value) or rejects (with an error). You do not wait for it; you attach a callback with .then, and that callback runs when the value arrives. In Lecture 5b, setTimeoutAsync(1000) was an imagined Promise version of setTimeout, used to show this idea; it is not a built-in function.

Works · .then and .catchconsole.log("fetching data");
fetchData()
  .then((data) => {
    console.log("here is your data:", data); // runs later, when data is ready
  })
  .catch((error) => {
    console.log("something went wrong:", error); // runs if the Promise rejects
  });
console.log("this line prints BEFORE the data arrives");

async/await is another way to write exactly the same thing. const data = await fetchData(); inside an async function does the same job as .then((data) => …), and try/catch plays the role of .catch. Use whichever you find easier to read. One rule: do not make the effect function itself async, because an effect may only return a cleanup function. Call .then inside it, or define an async helper inside it and call that.

Fetch on mount (planet explorer)

"Load the data when the screen opens" is an effect with an empty dependency array. This example has a pretend fetchData that resolves after one second, so it runs in Snack without a real server.

Works · App.tsximport { useState, useEffect } from "react";
import { View, Text, StyleSheet } from "react-native";

type Planet = { name: string; moons: number };

// Pretend server call: resolves with data after 1 second.
const fetchData = (): Promise<Planet[]> =>
  new Promise((resolve) => {
    setTimeout(() => {
      resolve([
        { name: "Mars", moons: 2 },
        { name: "Jupiter", moons: 95 },
      ]);
    }, 1000);
  });

export default function App() {
  const [planets, setPlanets] = useState<Planet[]>([]); // empty array needs a type

  useEffect(() => {
    fetchData().then((data) => setPlanets(data));
  }, []); // [] = once, after the first render

  return (
    <View style={styles.container}>
      {planets.length === 0 ? (
        <Text>Loading planets...</Text>
      ) : (
        planets.map((planet) => (
          <Text key={planet.name} style={styles.row}>
            {planet.name}: {planet.moons} moons
          </Text>
        ))
      )}
    </View>
  );
}

  container: { flex: 1, justifyContent: "center", padding: 24 },

});
Common trap.
  • No cleanup on an interval. Each new run of the effect starts another interval, and the clock speeds up. Always return () => clearInterval(id).
  • Missing dependency array plus a state update. useEffect(() => setCount(count + 1)) runs after every render, which causes a render, which runs the effect… forever.
  • setSeconds(seconds - 1) inside an interval with []. The stale closure freezes the clock. Use setSeconds((s) => s - 1).
  • Expecting data on the first render. The effect runs after the first render, so the screen must handle the empty starting state.
1. Which effect fetches data exactly once, when the screen first appears?
An empty array means "after the first render only". With no array, it runs after every render, and setting planets causes a render, so it would fetch over and over. With [planets], every new planets value triggers another fetch, which sets planets once more, and so on.
2. When does the cleanup function returned from an effect run?
React calls cleanup for you. It cleans up the previous run before starting the next one (when a dependency changed), and it cleans up when the component leaves the screen.

Interview craft

How to work during the 25 minutes

In one sentenceThe interviewer is watching your process, so read the handout, sketch the component tree, build one small step at a time in plain JavaScript, run it often, read every error, and talk while you work.

You are not expected to finish the whole problem. The handout gives you a reference screenshot and a step-by-step breakdown, and the TA may ask you to move on to a different step. What earns credit is showing that you can break a screen into components, wire up state and props, lay it out with Flexbox, and debug calmly. That is a skill you can rehearse, just like syntax.

1. Read the handout and decompose

  1. Read every step once, quickly, before writing code. Note which steps are layout, which are state, and which are callbacks.
  2. Find the data. What is the array, and what does one item look like? Write the type in your head (or in a comment): { name: string; popular: boolean }.
  3. Find the state. What changes on screen? Each changing thing is a useState. Where does it live? The lowest component that every user of it sits under.
  4. Find the events. Which taps or keystrokes change that state? Each one is a handler, defined where the state lives and passed down as a prop.
  5. Ask a clarifying question if a step is ambiguous. That is allowed and encouraged.

2. Sketch the component tree first

Boxes on the screenshot become components in your code. Thirty seconds of sketching saves five minutes of rewriting.

3. JavaScript first, run often

Build in thin slices and look at the preview after every one. A good order is: static layout with hard-coded text → map the real data → add state → add the handler and callback → add types. If something breaks, you know it was the last small thing you changed. Snack updates the preview as you type, so glance at it constantly.

4. Debug with console.log

When you are not sure what a value is, print it. Snack shows logs in the panel at the bottom of the editor. Label each log so you know which line printed it.

Works · labeled logsconst addMenuItem = (item: MenuItem) => {
  console.log("addMenuItem got:", item);  // did the child send the right object?
  setMenu([...menu, item]);
  console.log("menu right after set:", menu); // still the OLD array: state is a snapshot
};

console.log("render, menu has", menu.length, "items"); // runs every render

That second log surprises people: state does not change until the next render, so logging right after the setter shows the old value. Log at the top of the component to see the new value on the next render.

Squiggle or red screen? A red squiggle is a TypeScript complaint; it usually does not stop the app from running, which is exactly why "JS first, types second" works. A red error screen in the preview is a runtime error. Its first line usually tells you what went wrong, and it also shows the file and line number, so jump straight there. If the message does not make sense, searching the exact text is a great move.
Web preview vs phone. Snack's Web preview can behave differently from iOS or Android. Text outside <Text>, or a stray 0 from count && ..., may look fine on Web and only crash on a phone. If you can, check the iOS or Android preview (or Expo Go) before saying a step is done.

5. Think aloud

Talking lets the TA see your reasoning and point out a wrong assumption early. It feels strange at first, so rehearse a few sentences until they come naturally.
