How to practice

In one sentenceBuild every skill in three layers (plain JavaScript, then arrow functions as callbacks, then TypeScript) and climb the ladder: attempt, hint 1, hint 2, solution.

The most common sticking points in this interview are not exotic. They are the shape of an arrow function inside map, updating an array in state without mutating it, and passing a callback from a parent to a child. These exercises drill exactly those patterns, in several different apps, so you learn the pattern instead of memorizing one problem.

Layer 1 · Plain JavaScript

State, map, and arrow functions. Get it on screen first. Let inference type your state: useState(menuItems) is already MenuItem[].

Layer 2 · Arrows as callbacks

Handler in the parent, passed as a prop, called by the child inside an arrow: onPress={() => onAdd({ name, popular })}.

Layer 3 · Add TypeScript

Now type the data, the props, the callback props, empty arrays, and standalone parameters. Read each red squiggle as a sentence.

The ladder: attempt first

Give every exercise an honest attempt of at least five minutes before opening anything. If you're stuck, open Hint 1 (a nudge), then Hint 2 (names the exact API), and only then the solution. After reading a solution, close it and type it from memory; that last step is where it sticks.

Running an exercise in Snack

  1. Open snack.expo.dev and start a new Snack.
  2. Open App.tsx (rename App.js to App.tsx if needed) and replace everything with the starter code.
  3. Use the device preview (iOS or Android) when you can; the Web tab behaves slightly differently.
  4. Work through the // TODO markers. Red errors in the preview and red squiggles in the editor are clues, not failures of yours.

Mental model

Mental model: a component is a function

In one sentenceReact calls your component function on every render, so only state survives between renders, and only a setter tells React to redraw the screen.

Think of the screen as UI = f(state). Each render runs your component top to bottom, with the current state values. A plain variable inside the component is created fresh each time, and changing it does not ask React for a new render.

A local variable vs. state

You press the button three times. What does the first line on screen show? Decide before you reveal.

export default function App() {
  let count = 0;
  const [score, setScore] = useState(0);

  return (
    <View>
      <Text>count: {count}, score: {score}</Text>
      <Pressable
        onPress={() => {
          count = count + 1;
          setScore(score + 1);
        }}
      >
        <Text>Press me</Text>
      </Pressable>
    </View>
  );
}
Reveal answer
count: 0, score: 3
Why. Each press sets count to 1, but only inside that render's copy of the variable. setScore(score + 1) stores the new score in React and asks for a re-render, so App reruns from the top and let count = 0 makes a brand-new variable at 0. score survives because React keeps it between renders: 1, 2, 3. If you deleted the setScore line, the screen would never change at all, because assigning to count tells React nothing. A variable declared outside the component keeps its value, but it still never triggers a render. Rule: anything that should change what's on screen lives in useState and changes through its setter.

Rewrite four functions as arrow functions

Goal. Turn four classic function declarations into arrow functions. Use an expression body (no braces, no return) when the function is one expression, wrap a returned object in parentheses, and keep return when you use a block body with braces.

Starter code (App.tsx)
Starter · App.tsximport { View, Text, StyleSheet } from "react-native";

type Song = { title: string; artist: string; liked: boolean };

// TODO 1: rewrite as an arrow function with an EXPRESSION body (no braces, no return)
function double(n: number): number {
  return n * 2;
}

// TODO 2: rewrite as an arrow function with an expression body
function shout(word: string): string {
  return word.toUpperCase() + "!";
}

// TODO 3: rewrite as an arrow function that RETURNS AN OBJECT
//         (careful: braces right after => start a function body)
function makeSong(title: string, artist: string): Song {
  return { title: title, artist: artist, liked: false };
}

// TODO 4: rewrite as an arrow function with a BLOCK body (braces) and keep the return
function describe(song: Song): string {
  const status = song.liked ? "liked" : "not liked yet";
  return song.title + " by " + song.artist + " (" + status + ")";
}

export default function App() {
  const song = makeSong("Sunrise Drive", "The Maple Lights");
  return (
    <View style={styles.container}>
      <Text style={styles.line}>double(21) gives {double(21)}</Text>
      <Text style={styles.line}>shout gives {shout("hello")}</Text>
      <Text style={styles.line}>{describe(song)}</Text>
    </View>
  );
}

const styles = StyleSheet.create({
  container: { flex: 1, paddingTop: 60, paddingHorizontal: 20, backgroundColor: "#f6f7fc" },
  line: { fontSize: 18, marginBottom: 10 },
});
Show hint 1

Every rewrite starts the same way: const name = (params) => .... Then ask: is the body a single expression? If yes, drop the braces and the word return.

Show hint 2

For TODO 3, an object literal right after => must be wrapped: => ({ title, artist, liked: false }). Without the parentheses, JavaScript reads { as the start of a function body. For TODO 4, a block body is => { ...; return value; }.

Show solution
Solution · App.tsximport { View, Text, StyleSheet } from "react-native";

type Song = { title: string; artist: string; liked: boolean };

// 1. Expression body: the value after => is returned automatically
const double = (n: number): number => n * 2;

// 2. Same idea; the return type (string) is inferred
const shout = (word: string) => word.toUpperCase() + "!";

// 3. Returning an object: wrap it in ( ) so { } is not read as a body.
//    { title, artist } is shorthand for { title: title, artist: artist }
const makeSong = (title: string, artist: string): Song => ({
  title,
  artist,
  liked: false,
});

// 4. Block body: braces mean "statements", so return is required
const describe = (song: Song) => {
  const status = song.liked ? "liked" : "not liked yet";
  return `${song.title} by ${song.artist} (${status})`;
};

export default function App() {
  const song = makeSong("Sunrise Drive", "The Maple Lights");
  return (
    <View style={styles.container}>
      <Text style={styles.line}>double(21) gives {double(21)}</Text>
      <Text style={styles.line}>shout gives {shout("hello")}</Text>
      <Text style={styles.line}>{describe(song)}</Text>
    </View>
  );
}

const styles = StyleSheet.create({
  container: { flex: 1, paddingTop: 60, paddingHorizontal: 20, backgroundColor: "#f6f7fc" },
  line: { fontSize: 18, marginBottom: 10 },
});
Why this works. An arrow function has two shapes. Expression body: (x) => x * 2 returns the expression with no return keyword. Block body: (x) => { ... } runs statements, and returns undefined unless you write return. An object literal also uses braces, so => { title } is read as a block. Wrapping it as => ({ title }) tells JavaScript you mean a value. These are exactly the two shapes you use inside map and in onPress.
Common mistakes
  • Writing const makeSong = (title, artist) => { title, artist, liked: false };. Braces start a body, so this is a syntax error (or, with a single property, silently returns undefined).
  • Keeping braces but forgetting return: (n) => { n * 2 } returns undefined.
  • Using the arrow before the line that defines it. const arrow functions are not hoisted the way function declarations are, so define helpers above where you call them.

Solution · App.tsximport { useState } from "react";
import { View, Text, Pressable, StyleSheet } from "react-native";

type FruitData = { price: number; emoji: string };

const fruitList: FruitData[] = [
  { price: 2, emoji: "🍎" },
  { price: 3, emoji: "🍑" },
  { price: 5, emoji: "🍋" },
  { price: 8, emoji: "🍌" },
];

export default function App() {
  const [total, setTotal] = useState(0);

  const addToCart = (price: number) => {
    setTotal(total + price);
  };

  // One-liner map: no { after =>, so the JSX is returned automatically
  const buttons = fruitList.map((fruit) => (
    <Pressable
      key={fruit.emoji}
      style={styles.fruit}
      // A function VALUE: it runs only when the user presses
      onPress={() => addToCart(fruit.price)}

      <Text style={styles.emoji}>{fruit.emoji}</Text>
      <Text style={styles.price}>${fruit.price}</Text>
    </Pressable>
  ));

  return (
    <View style={styles.container}>
      <Text style={styles.total}>Total: ${total}</Text>
      <View style={styles.grid}>{buttons}</View>
      <Pressable style={styles.clear} onPress={() => setTotal(0)}>
        <Text style={styles.clearText}>Clear</Text>
      </Pressable>
    </View>
  );
}

const styles = StyleSheet.create({
  container: { flex: 1, paddingTop: 60, paddingHorizontal: 20, backgroundColor: "#f6f7fc" },

  grid: { flexDirection: "row", flexWrap: "wrap", gap: 12 },

  clearText: { color: "#ffffff", fontSize: 17, fontWeight: "700" },
});
Why this works. There are three things you can put in onPress: f (pass the function itself), f() (call it now and pass its result), and () => f(x) (pass a new function that will call f(x) later). You need the third one whenever the handler needs an argument, like the price of this fruit. Because each arrow is created inside map, it remembers its own fruit.
Common mistakes
  • onPress={addToCart(fruit.price)} calls addToCart during render. That sets state, which renders, which calls it, and so on: Too many re-renders. React limits the number of renders to prevent an infinite loop.
  • onPress={addToCart} passes the function, but React Native calls it with a press event, not a price. TypeScript flags this because the event is not a number.
  • Forgetting key={fruit.emoji} on the Pressable that map returns.

    // Updater form: React passes in the latest value (including queued updates)
    setChapters((c) => c + 1);
  };

  const readThree = () => {
    // Three queued updaters: c => c + 1, three times, so +3
    readOne();
    readOne();
    readOne();
  };

  const setAndLog = () => {
    setChapters(chapters + 1);
    // Shows the OLD value: `chapters` is this render's snapshot.
    // The new value only exists in the NEXT render.
    setLog("Right after setting: " + chapters);
  };

  return (

      <Text style={styles.title}>Book club</Text>
      <Text style={styles.big}>{chapters}</Text>

          <Text style={styles.buttonText}>+3</Text>
        </Pressable>
      </View>

Why this works. A setter accepts either a next value (setChapters(chapters + 1)) or an updater function (setChapters((c) => c + 1)). Both are correct. The direct form is the simplest default. The updater form is safer when the new value depends on the old one and several updates can happen before the next render, as here or inside a timer. React batches updates during an event and applies the queued updaters in order.
Common mistakes
  • Forgetting that the updater form exists. A setter takes either a new value or a function prev => newValue; both are part of the useState API.
  • Calling setChapters(chapters + 3) to "fix" it. That works for this button, but it hides the real lesson about snapshots.
  • Putting side effects (like setLog) inside an updater function. Updaters should only compute and return the next value.

Solution · App.tsximport { useState, useEffect } from "react";
import { View, Text, Pressable, StyleSheet } from "react-native";

const SPRINT_SECONDS = 60;

export default function App() {
  const [secondsLeft, setSecondsLeft] = useState(SPRINT_SECONDS);
  const [running, setRunning] = useState(false);

  // Runs after the first render and whenever `running` changes
  useEffect(() => {
    if (!running) return; // paused: no interval, nothing to clean up

    const id = setInterval(() => {
      // Updater form: always uses the latest value, not a stale snapshot
      setSecondsLeft((s) => (s > 0 ? s - 1 : 0));
    }, 1000);

    // Cleanup: runs before the effect re-runs (running changed) and on unmount
    return () => clearInterval(id);
  }, [running]);

  // Stop automatically at zero
  useEffect(() => {
    if (secondsLeft === 0) setRunning(false);
  }, [secondsLeft]);

  const reset = () => {
    setRunning(false);
    setSecondsLeft(SPRINT_SECONDS);
  };

  const minutes = Math.floor(secondsLeft / 60);
  const seconds = String(secondsLeft % 60).padStart(2, "0");

  return (
    <View style={styles.container}>
      <Text style={styles.title}>Writing sprint</Text>
      <Text style={styles.big}>
        {minutes}:{seconds}
      </Text>
      <Text style={styles.sub}>{secondsLeft === 0 ? "Time! Pens down." : "Keep going!"}</Text>
      <View style={styles.row}>
        <Pressable
          style={styles.button}
          // Don't start a finished sprint; Reset first
          onPress={() => setRunning(!running && secondsLeft > 0)}
        >
          <Text style={styles.buttonText}>{running ? "Pause" : "Start"}</Text>
        </Pressable>
        <Pressable style={styles.ghost} onPress={reset}>
          <Text style={styles.ghostText}>Reset</Text>
        </Pressable>
      </View>
    </View>
  );
}

Why this works. The interval is an external system: React doesn't manage it, so you start it in an effect and stop it in the cleanup. With [running], pressing Pause changes running, React runs the cleanup (clearing the old interval), and the effect re-runs and does nothing. The updater form matters because the interval callback was created during one render; with setSecondsLeft(secondsLeft - 1) it would keep using that render's snapshot and get stuck at 59.
Common mistakes
  • Calling setInterval directly in the component body. It starts a new interval on every render, and they pile up.
  • Forgetting the cleanup. Each Start adds another interval, so the countdown speeds up.
  • Leaving out the dependency array: useEffect(fn) runs after every render, so the interval would be torn down and restarted every second.
